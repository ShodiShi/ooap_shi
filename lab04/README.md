# Менеджер заметок

## Описание предметной области

В этой работе рассматривается приложение для работы с заметками. Пользователь может создавать заметки, редактировать их, удалять, распределять по категориям, импортировать заметки из текстовых файлов и экспортировать заметку в `.txt`.

Также в проекте есть дополнительные функции: просмотр статистики заметки, экспорт заметки и импорт заметок из файлов. Идея импорта заметок с телефона реализована через экспорт заметки в файл и последующий импорт этого файла в приложение.

Прямое подключение к Samsung Notes не используется, потому что у Samsung Notes нет удобного и стабильного открытого API для такой задачи. Поэтому был выбран более простой и реалистичный вариант: пользователь экспортирует заметку с телефона в файл, а приложение импортирует этот файл.

## Проблема

Если делать такое приложение без паттерна, то все дополнительные функции начинают попадать в главный класс интерфейса. В моем случае это `MainController`.

Например, без паттерна в одном контроллере оказываются методы:

- `showStatistics()`
- `exportTxt()`
- `importFromFile()`
- `importFromFolder()`

Из-за этого класс становится слишком большим. Если потом нужно добавить новую функцию, приходится снова менять `MainController`. Это неудобно, потому что контроллер начинает отвечать сразу и за интерфейс, и за дополнительную логику приложения.

Основная проблема: приложение должно расширяться новыми функциями, но без паттерна расширение делает главный код более запутанным.

## Используемый паттерн

Для решения этой проблемы в основной версии проекта используется паттерн **Plugin**.

Смысл паттерна в том, что дополнительная функциональность выносится в отдельные модули. Каждый модуль реализует общий интерфейс `Plugin`, а основное приложение запускает плагины через `PluginManager`.

В проекте были сделаны такие плагины:

- `StatisticsPlugin` — показывает статистику заметки;
- `ExportTxtPlugin` — экспортирует заметку в текстовый файл;
- `ImportFilePlugin` — импортирует заметку из файла;
- `ImportFolderPlugin` — импортирует заметки из папки.

## Как используется паттерн

В проекте есть общий интерфейс:

```java
public interface Plugin {
    String getName();

    void execute(PluginContext context);
}
```

Все плагины реализуют этот интерфейс. Благодаря этому приложение может работать с разными плагинами одинаково.

Например, в версии с паттерном плагины регистрируются так:

```java
pluginManager.registerPlugin(new StatisticsPlugin());
pluginManager.registerPlugin(new ExportTxtPlugin());
pluginManager.registerPlugin(new ImportFilePlugin());
pluginManager.registerPlugin(new ImportFolderPlugin());
```

Потом в интерфейсе для каждого плагина создается кнопка. При нажатии кнопки вызывается не конкретный метод контроллера, а общий запуск через `PluginManager`:

```java
pluginManager.executePlugin(name, context);
```

Внутри `PluginManager` происходит поиск нужного плагина по имени и вызов метода:

```java
plugin.execute(context);
```

То есть главное приложение не знает подробностей работы конкретного плагина. Оно только знает, что любой плагин можно запустить через `execute`.

## Зачем нужен PluginContext

`PluginContext` нужен для передачи данных в плагин.

Например, плагину может понадобиться:

- выбранная заметка;
- окно приложения;
- сервис импорта;
- репозиторий заметок;
- репозиторий категорий.

Чтобы не передавать все это отдельными параметрами, используется один объект `PluginContext`.

## База данных

В проекте используется SQLite. База данных хранится в файле `notes.db`.

В основной версии с паттерном используются таблицы:

- `categories` — категории заметок;
- `notes` — сами заметки;
- `imports` — информация об импортированных файлах;
- `plugins` — список плагинов;
- `plugin_settings` — настройки плагинов.

Таблица `plugins` нужна для хранения информации о доступных модулях. Через нее можно включать и выключать плагины.

## Версия без паттерна

Для сравнения была сделана отдельная версия приложения без паттерна.

В ней нет:

- интерфейса `Plugin`;
- класса `PluginManager`;
- класса `PluginContext`;
- отдельных классов-плагинов.

Все функции вызываются напрямую из `MainController`.

Пример:

```java
addToolButton(box, "Статистика", this::showStatistics);
addToolButton(box, "Экспорт в TXT", this::exportTxt);
addToolButton(box, "Импорт файла", this::importFromFile);
addToolButton(box, "Импорт папки", this::importFromFolder);
```

То есть кнопка сразу вызывает обычный метод контроллера. Такая реализация работает, но контроллер становится перегруженным.

## Сравнение вариантов

Без паттерна:

- вся дополнительная логика находится в `MainController`;
- контроллер становится большим;
- новые функции добавляются через изменение уже существующего класса;
- сложнее сопровождать код.

С паттерном:

- каждая функция вынесена в отдельный плагин;
- все плагины имеют общий интерфейс;
- запуском занимается `PluginManager`;
- новые функции можно добавлять отдельными классами;
- плагины можно включать и выключать.

## Вывод

Внедрение паттерна `Plugin` сделало программу более удобной для расширения. Дополнительные функции перестали быть просто набором методов внутри `MainController` и были вынесены в отдельные классы.

За счет этого основной код стал понятнее. Если нужно добавить новую функцию, можно создать новый класс-плагин и зарегистрировать его в `PluginManager`, а не переписывать главный контроллер.

Также паттерн позволил сделать управление модулями через базу данных: плагины можно включать и выключать. В версии без паттерна такой механизм пришлось бы делать вручную прямо в контроллере.

Итог: паттерн `Plugin` уменьшил связанность кода, упростил добавление новых функций и сделал архитектуру приложения более аккуратной.
