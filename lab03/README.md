# 🎵 Music Player — Паттерн «Состояние»

>  Реализация паттерна проектирования «Состояние» на примере музыкального плеера.

---

## 1. Описание проблемы

Музыкальный плеер в любой момент времени находится в одном из трёх состояний: **воспроизведение**, **пауза** или **остановлен**. Поведение плеера при нажатии на кнопки зависит от текущего состояния:

| Действие | Stopped | Playing | Paused |
|----------|---------|---------|--------|
| play() | Начать воспроизведение | Ничего не делать | Возобновить с места паузы |
| pause() | Ничего не делать | Поставить на паузу | Ничего не делать |
| stop() | Ничего не делать | Остановить | Остановить |
| next() | Перейти к следующему | Перейти к следующему | Перейти к следующему |

**Проблема без паттерна:** в каждом методе класса `Player` появляются цепочки условий `if/elif`, которые проверяют текущее состояние:

```python
def play(self):
    if self.status == "stopped":
        # начать с начала
    elif self.status == "playing":
        # уже играет, ничего не делать
    elif self.status == "paused":
        # возобновить с места паузы
```

Такой код трудно поддерживать — при добавлении нового состояния придётся вносить изменения в каждый метод. Это нарушает принцип открытости/закрытости (OCP).

---

## 2. Решение: паттерн «Состояние»

Паттерн **«Состояние»** позволяет объекту менять своё поведение при изменении внутреннего состояния. Поведение каждого состояния выносится в отдельный класс.

### Как используется в проекте

- **`PlayerState`** — абстрактный класс, задающий контракт: каждое состояние обязано реализовать методы `play()`, `pause()`, `stop()`, `next()`, `prev()`.
- **`StoppedState`**, **`PlayingState`**, **`PausedState`** — конкретные классы состояний, каждый реализует методы по-своему.
- **`Player`** — контекст, хранит ссылку на текущее состояние и делегирует ему все вызовы:

```python
def play(self):
    self.state.play(self)  # делегируем текущему состоянию
```

При необходимости сменить состояние — конкретный класс состояния сам вызывает `player.set_state(NewState())`. Никаких `if/elif` в `Player` больше нет.

## 6. Вывод

Внедрение паттерна «Состояние» повлияло на архитектуру проекта следующим образом:

**До паттерна** — класс `Player` содержал разветвлённые условия `if/elif` в каждом методе. При добавлении нового состояния пришлось бы изменять все методы класса, что увеличивало риск ошибок и нарушало принцип открытости/закрытости.

**После паттерна** — каждое состояние инкапсулировано в отдельном классе. Класс `Player` не знает о деталях реализации состояний — он просто делегирует вызовы текущему состоянию. Добавление нового состояния требует создания только одного нового класса без изменения существующего кода.

Таким образом, паттерн «Состояние» сделал код более читаемым, расширяемым и соответствующим принципам SOLID.
